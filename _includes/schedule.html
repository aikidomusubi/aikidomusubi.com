{%- comment -%} Weekly training timetable, rendered at build time from _data/schedule.yml. Everything here is static HTML. There is no calendar library, no fetch, and no client-side rendering: the class times are in the markup, so they are indexable, readable with JavaScript off, and cost nothing on the main thread. scripts/schedule.js only adds filtering, day tabs and the now-line on top. Layout comes from the times themselves. Each block is placed with CSS Grid row numbers computed below from `start` and `end`, which is what replaced the hand-tuned "height: 6rem; margin-top: -11.5rem" offsets the old data carried. Change a time in the YAML and the block moves; nothing else to update. Two coordinate tricks are worth knowing before editing: * Times are compared and sorted as zero-padded "HH:MM" strings. That is lexicographically equivalent to comparing them as times, which lets Liquid sort and overlap-test without any date parsing. * The grid skips the empty middle of the day. `meta.bands` lists the periods that actually contain classes, and a time's row is its offset within the concatenation of those bands — see `band_offset` below. {%- endcomment -%} {%- assign S = site.data.schedule -%} {%- assign L = page.lang | default: 'es' -%} {%- assign slot = S.meta.slot_minutes -%} {%- comment -%} Column order. The data is written Monday-first; English and Japanese readers expect the week to start on Sunday, so the display order is rotated rather than the data being duplicated. See `week_start` in _data/schedule.yml. {%- endcomment -%} {%- if S.week_start[L] == 'sun' -%} {%- assign week_days = 'sun,mon,tue,wed,thu,fri,sat' | split: ',' -%} {%- else -%} {%- assign week_days = 'mon,tue,wed,thu,fri,sat,sun' | split: ',' -%} {%- endif -%} {%- comment -%} Total rows: sum of every band's length in slots. {%- endcomment -%} {%- assign total_rows = 0 -%} {%- for b in S.meta.bands -%} {%- assign bs = b.start | split: ':' -%}{%- assign bsm = bs[0] | times: 60 | plus: bs[1] -%} {%- assign be = b.end | split: ':' -%}{%- assign bem = be[0] | times: 60 | plus: be[1] -%} {%- assign len = bem | minus: bsm | divided_by: slot -%} {%- assign total_rows = total_rows | plus: len -%} {%- endfor -%}

{%- comment -%} Structured data. THESE ARE COURSES, NOT EVENTS, AND CALLING THEM EVENTS WAS A CRITICAL ERROR. Each class used to be an `Event` with an `eventSchedule` describing the weekly repeat. That reads well and it is invalid: Google requires `startDate` on every Event and a class that runs every Tuesday has no single one. Search Console reported all seventeen as `Missing field "startDate"` and, with it, endDate, offers, image and performer — so the whole block was seventeen permanent errors attached to markup that could never produce a rich result. Same reasoning that took the Events report from 44 invalid to 0 in September: an item that is not eligible is decoration, and decoration with errors on it is worse than none. A recurring class offered by an organisation is a `Course` whose `hasCourseInstance` carries the `Schedule`. `CourseInstance` is defined to need no start date, which is the whole point of it, and the same repeat information survives unchanged. Inventing a startDate was the other option and it is the wrong one: the next Tuesday is a fact that goes stale on Wednesday, and a static site cannot regenerate it. Emitted from the same data as the grid above, so the two cannot disagree. {%- endcomment -%} {%- assign DAYMAP = 'mon:Monday,tue:Tuesday,wed:Wednesday,thu:Thursday,fri:Friday,sat:Saturday,sun:Sunday' | split: ',' -%}
